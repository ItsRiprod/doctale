# Built-in Plugins Reference

Hytale ships with 32 built-in plugin packages that demonstrate modding patterns and provide core gameplay features. Some packages (notably `adventure/`) contain multiple independent plugin classes — the actual plugin count is over 45. This reference documents each plugin, its components, and how to learn from them.

## Package Location

`com.hypixel.hytale.builtin`

## WeatherPlugin

**Location**: `builtin/weather/`

Manages dynamic weather systems per world.

### Components

| Component | Store | Description |
|-----------|-------|-------------|
| `WeatherTracker` | EntityStore | Tracks weather per player |
| `WeatherResource` | EntityStore | World weather state |

### Systems

```java
WeatherSystem.WorldAddedSystem    // Initialize weather for new worlds
WeatherSystem.PlayerAddedSystem   // Send weather to joining players
WeatherSystem.TickingSystem       // Update weather over time
WeatherSystem.InvalidateWeatherAfterTeleport  // Sync after teleport
```

### Commands

- `/weather <type>` - Change weather

<Aside type="note" title="New in Update 4">
Weather randomization is now deterministic. The weather seed is computed from `worldSeed + environment.getWeatherSeedKey().hashCode() + dateTime.hashCode()` using `FastRandom` instead of `ThreadLocalRandom`. Environments can share weather forecasts by using the same `weatherSeedKey`.
</Aside>

### Key Patterns

```java
// Register resource
weatherResourceType = EntityStore.REGISTRY.registerResource(
    WeatherResource.class, WeatherResource::new);

// Register component
weatherTrackerComponentType = EntityStore.REGISTRY.registerComponent(
    WeatherTracker.class, WeatherTracker::new);

// Register systems
entityStoreRegistry.registerSystem(new WeatherSystem.TickingSystem());
```

## CraftingPlugin

**Location**: `builtin/crafting/`

Complete crafting system with benches, recipes, and UI.

### Components

| Component | Store | Description |
|-----------|-------|-------------|
| `CraftingManager` | EntityStore | Player crafting state |
| `BenchBlock` | ChunkStore | Crafting bench block component |
| `ProcessingBenchBlock` | ChunkStore | Processing bench block component |

<Aside type="caution" title="Changed in Update 4">
`BenchState` and `ProcessingBenchState` (which extended `BlockState`) have been replaced by `BenchBlock` and `ProcessingBenchBlock` (`Component<ChunkStore>`). Register them via `getChunkStoreRegistry().registerComponent()` instead of `blockStateRegistry.registerBlockState()`. Lifecycle logic previously in the state classes is now in `BenchSystems` (inner classes `OnAddOrRemoved`, `ProcessingBenchTick`, `ProcessingBenchLifecycle`). `CraftRecipeEvent.Pre` and `CraftRecipeEvent.Post` events are now dispatched during crafting, allowing plugins to cancel or modify recipe results.
</Aside>

### Block Components

```java
// Register block component for crafting benches
getChunkStoreRegistry().registerComponent(
    BenchBlock.class, BenchBlock::new);
```

### Interactions

```java
OpenBenchPageInteraction        // Open crafting UI
OpenProcessingBenchInteraction  // Open processing UI
LearnRecipeInteraction          // Learn new recipe
```

### Recipe System

```java
// Get recipes for a bench
List<CraftingRecipe> recipes = CraftingPlugin.getBenchRecipes(bench);

// Learn a recipe
CraftingPlugin.learnRecipe(ref, recipeId, componentAccessor);

// Check if item is valid material
CraftingPlugin.isValidCraftingMaterialForBench(bench, itemStack);
```

### Commands

- `/recipe learn <id>` - Learn recipe
- `/recipe forget <id>` - Forget recipe

## FluidPlugin

**Location**: `builtin/fluid/`

Fluid simulation and water physics.

### Key Features

- Water flow simulation
- Fluid level tracking
- Swimming mechanics

### Registrations

FluidPlugin registers three `FluidTicker` codecs and six `FluidSystems` that operate on core chunk components (`FluidSection`, `ChunkSection`, `BlockChunk`, `ChunkColumn`, `WorldChunk`).

| FluidTicker Codec | Class | Description |
|-------------------|-------|-------------|
| `Default` | `DefaultFluidTicker` | Standard fluid spreading |
| `Fire` | `FireFluidTicker` | Fire fluid behavior |
| `Finite` | `FiniteFluidTicker` | Finite fluid volumes |

<Aside type="note" title="New in Update 4">
`DisabledFluidResource` is a new `Resource<ChunkStore>` that caches disabled fluid IDs from `WorldConfig.getDisabledFluidTickers()`. This allows per-world control over which fluids tick. When a fluid ID is in the disabled set, its tick is skipped entirely.
</Aside>

## BlockTickPlugin

**Location**: `builtin/blocktick/`

Deterministic block update and tick system.

### Systems

```java
ChunkBlockTickSystem       // Process block ticks
MergeWaitingBlocksSystem   // Merge pending updates
```

### Tick Procedures

```java
BasicChanceBlockGrowthProcedure      // Simple growth
SplitChanceBlockGrowthProcedure      // Variable growth rates
```

<Aside type="note" title="New in Update 3">
For random (non-deterministic) block ticking, see `RandomTickPlugin` which was added in Update 3. `BlockTickPlugin` handles deterministic per-block ticking via `TickProcedure`, while `RandomTickPlugin` handles random selection of blocks per chunk section. For a complete list of what changed, check the [Update 3 changelog](/changelog/update-2-to-3/).
</Aside>

## BedsPlugin

**Location**: `builtin/beds/`

Bed interactions and spawn points.

### Key Features

- Sleep mechanics
- Individual spawn points
- Respawn handling
- Multiplayer sleep notifications

<Aside type="note" title="New in Update 3">
A `SleepNotificationSystem` was added for multiplayer sleep coordination. On small servers (4 or fewer players), all awake players are notified when someone tries to sleep. On larger servers, notifications trigger when the sleeper ratio reaches 50%. Sleep sound configuration support was also added. See the [Update 3 changelog](/changelog/update-2-to-3/) for all builtin plugin changes.
</Aside>

## VoiceModule (Core)

**Location**: `server/core/modules/voice/`

<Aside type="note" title="New in Update 4">
VoiceModule is a core server module, not a builtin plugin. It is documented here because it is a significant new system modders may interact with.
</Aside>

Proximity voice chat system with spatial audio routing.

### Configuration

| Field | Default | Description |
|-------|---------|-------------|
| `voiceEnabled` | true | Enable/disable voice chat |
| `maxHearingDistance` | 32 | Maximum distance to hear other players |
| `fullVolumeDistance` | 4 | Distance at which voice is at full volume |
| `deadPlayersCanHear` | — | Whether dead players can still hear voice |
| `mutedPlayers` | empty | Set of muted player UUIDs |

### Key Details

- Uses dedicated QUIC streams via `StreamManager.registerHandler(StreamType.Voice, ...)`
- Maximum 12 simultaneous speakers per listener
- Speaker positions quantized to 0.5 block resolution
- Rate limited to 60 packets/second with burst capacity of 25
- 4 dedicated executor threads

### Commands

- `/voice enabled <true|false>` - Toggle voice chat
- `/voice maxdistance <distance>` - Set max hearing distance
- `/voice mute <player>` - Mute a player
- `/voice unmute <player>` - Unmute a player
- `/voice status` - Show voice chat status

## Common Patterns

### Plugin Singleton Pattern

```java
public class MyPlugin extends JavaPlugin {
    private static MyPlugin instance;

    public static MyPlugin get() {
        return instance;
    }

    public MyPlugin(JavaPluginInit init) {
        super(init);
        instance = this;
    }
}
```

### Component Registration Pattern

```java
@Override
protected void setup() {
    // Register component
    myComponentType = EntityStore.REGISTRY.registerComponent(
        MyComponent.class, MyComponent::new);

    // Register system
    getEntityStoreRegistry().registerSystem(new MySystem());
}
```

### Event Registration Pattern

```java
@Override
protected void setup() {
    // Register event listener
    getEventRegistry().register(LoadedAssetsEvent.class, Item.class,
        this::onItemLoad);

    // Register global listener
    getEventRegistry().registerGlobal(AddWorldEvent.class,
        event -> initializeWorld(event.getWorld()));
}
```

### Command Registration Pattern

```java
@Override
protected void setup() {
    // Via CommandRegistry
    getCommandRegistry().registerCommand(new MyCommand());

    // Via CommandManager (system commands)
    CommandManager.get().registerSystemCommand(new MySystemCommand());
}
```

### Codec Registration Pattern

```java
@Override
protected void setup() {
    // Register interaction type
    getCodecRegistry(Interaction.CODEC)
        .register("MyInteraction", MyInteraction.class, MyInteraction.CODEC);

    // Register block component
    getChunkStoreRegistry().registerComponent(
        MyBlockComponent.class, MyBlockComponent::new);
}
```

### World Event Pattern

```java
@Override
protected void setup() {
    getEventRegistry().registerGlobal(AddWorldEvent.class, event -> {
        World world = event.getWorld();
        // Initialize per-world state
        world.getWorldMapManager().addMarkerProvider("markers", myProvider);
    });
}
```

<Aside type="caution" title="Changed in Update 3">
The `MarkerProvider` interface changed from returning `List<MapMarker>` to `void provide(World, Player, MarkersCollector)`. Marker providers now use `MarkersCollector` to add markers with distance-based filtering. `PlayerIconMarkerProvider` was replaced by `OtherPlayersMarkerProvider`, and `PerWorldDataMarkerProvider` was split into `PersonalMarkersProvider` and `SharedMarkersProvider`. A new user-created map marker system (`UserMapMarker`, `UserMapMarkersStore`) was also added. The [Update 3 changelog](/changelog/update-2-to-3/) documents all marker system changes.
</Aside>
